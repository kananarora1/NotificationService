# Build Delivery Truth Before Adding Intelligence

**Add an observability agent, but only as a constrained, read-only incident reporter after the service has correlated, redacted telemetry and actionable alerts.** The current service already has a sound asynchronous core—Postgres-backed notification state, RabbitMQ publisher confirms, retry/DLQ handling, a lease reconciler, tenant API-key isolation, rate limiting, and Prometheus/Grafana metrics—but its `SENT` state reflects a simulated provider call rather than confirmed customer delivery. The next product investment should therefore make delivery accountable to customers: immutable attempt history, real-provider callbacks, and tenant-scoped status first; signed customer webhooks and templates second; scheduling, preferences, and provider routing only after that core works. An AI model will not repair missing lifecycle evidence and would create a sensitive, high-risk production dependency if given raw logs or operational access. A deterministic incident-enricher can deliver most of the immediate operational value, while a later agent can summarize its bounded evidence pack into a developer-ready hypothesis and next checks. This sequencing makes the service safer to operate and gives the eventual agent facts to reason from rather than secrets and noisy text.

## Delivery state should become the customer contract

The service reliably accepts and recovers work, but its externally meaningful lifecycle stops too early. It exposes only `PENDING`, `SENDING`, `SENT`, and `DEAD`; `SENT` follows `SimulatedProvider.send`, whose own documentation says it does not perform real delivery. Preserve the existing current-state row, but add immutable `notification_event` and `delivery_attempt` records containing provider message ID, bounded failure category/code, timestamps, attempt number, and source callback ID. Then make `GET /v1/notifications/{id}` return an explicit progression such as accepted, queued, dispatched, provider-accepted, delivered, failed, expired, cancelled, or preference-suppressed. This is more valuable than a campaign feature because it lets an integrator distinguish an HTTP 202 from delivery.

A real provider adapter should submit with its provider-side idempotency key, verify signed status callbacks, deduplicate callback event IDs, and allow only valid forward state transitions. Provider callbacks are the scalable source of truth: Twilio, for example, emits sent, delivered, failed, undelivered, and (where supported) read status changes, and recommends callbacks rather than high-volume polling ([Twilio status callbacks](https://www.twilio.com/docs/messaging/guides/outbound-message-status-in-status-callbacks)). Keep the existing RabbitMQ confirms and lease recovery—they protect the service’s own delivery pipeline—but do not mistake a broker confirm or provider acceptance for recipient delivery. The durable outbox pattern remains a sensible future hardening step when state writes and publication need one transaction; until then, the existing `published_at` reconciler provides a practical recovery path for unconfirmed publishes.

## Integrator-facing features deliver the next value

After delivery truth, build signed tenant callback webhooks. A `notification.delivered` or `notification.failed` event with a stable event ID lets a customer update an order, password-reset, or support workflow without polling. Treat this as a second delivery system: persist endpoint and delivery records, send through the outbox/attempt framework, sign payloads with a versioned HMAC and timestamp, retry with bounded backoff, retain an audited history, and offer a test event. Endpoint registration must be tenant-admin-only and SSRF-resistant—permit HTTPS only, reject private/link-local destinations after DNS resolution, cap redirects, timeouts, and response size, and never forward credentials.

Next add a deliberately narrow template library: immutable versioned templates by channel and locale, typed variables, preview, channel-specific escaping and length validation, and the exact version recorded on every notification. It gives customers safe reuse of transactional copy without allowing a general scripting engine. Add recipient preferences, consent provenance, quiet hours, and a distinct `SUPPRESSED_PREFERENCE` outcome before any marketing or bulk capability; enforcing preferences both before enqueue and just before dispatch prevents unwanted paid sends. Scheduling, cancellation, and `deliver_by` expiry follow naturally once those state transitions exist: persist UTC schedule/expiry plus the supplied IANA zone, let clustered workers claim due work from Postgres, and make cancellation win only before a delivery attempt is claimed. Defer campaign builders, arbitrary template logic, automatic cross-provider resend, and active-active multi-region delivery: each magnifies consent, duplicate-send, and incident risk before the service can explain a single notification end to end.

## Existing metrics support alerts, not investigations

The repository already ships Actuator/Micrometer, Prometheus, Grafana, business counters, queue/dead-letter gauges, and carefully documented alerts for permanent failures, backlog, latency, stranded leases, and unpublished accepted requests. That is a strong starting point. It lacks structured JSON event logs, end-to-end traces, log/trace correlation, provider callback evidence, and a production provider; the current log lines can also expose recipient addresses and must not become an agent data source unchanged. Instrument the API, publisher, consumer, reconciler, provider adapter, callback endpoint, Redis limiter, and persistence boundaries with a stable event catalogue. Include event name, severity, trace/span IDs, service/version/environment, hashed notification and tenant identifiers, channel, state transition, attempt, bounded outcome/error type, and elapsed time; exclude message body, recipient contact data, API keys, authorization headers, credentials, and arbitrary AMQP headers. OpenTelemetry’s logs model defines trace/span correlation and resource context ([OpenTelemetry Logs](https://opentelemetry.io/docs/specs/otel/logs/)), while its URL guidance warns that captured URL data can expose sensitive values ([OpenTelemetry URL conventions](https://opentelemetry.io/docs/specs/otel/semconv/url/)).

Use Micrometer tracing with an OTLP exporter and propagate W3C trace context from HTTP into allowed RabbitMQ headers and out to provider calls. Spring Boot’s observability support depends on its instrumented client builders for propagation, so manually constructed provider clients should be avoided ([Spring Boot tracing](https://docs.spring.io/spring-boot/3.5/reference/actuator/tracing.html)). Keep Prometheus for bounded-cardinality metrics and alerts; never label a metric with notification ID, recipient, trace ID, raw error message, or unconstrained tenant ID. If Loki is adopted, keep the same identifiers as parsed fields or structured metadata, not stream labels—Loki specifically cautions against high-cardinality labels such as trace and request IDs ([Loki label guidance](https://grafana.com/docs/loki/latest/get-started/labels/bp-labels/)). Alert on customer impact and imminent hard limits, and attach a dashboard and runbook to every page; actionable, user-symptom-oriented alerts are the SRE standard ([Google SRE incident management](https://sre.google/resources/practices-and-processes/incident-management-guide/)).

## Make the agent an evidence pack, not an operator

Start with an internal `incident-enricher`, not an LLM. It should authenticate Alertmanager or Grafana webhooks, deduplicate by environment and alert fingerprint, clamp an incident time window, run a fixed evidence pack, preserve query parameters and source links, and post a deterministic report. The pack should cover alert lifecycle and SLO context; bounded metric windows; redacted error-event samples; exemplar traces; RabbitMQ ready/unacked/dead-letter signals; Postgres/Redis health; deployment or configuration changes; dashboard and runbook links. Grafana’s alert notification payload already provides status, labels, annotations, timestamps, fingerprint, and dashboard/generator URLs, so this flow need not scrape a dashboard ([Grafana notification data](https://grafana.com/docs/grafana/latest/alerting/configure-notifications/template-notifications/reference/)).

Only after that flow is dependable should a developer request a constrained analysis agent. Give it an immutable evidence pack first and, for gaps, typed read-only tools such as `get_alert`, approved metric/log/trace templates, queue/dependency snapshots, and curated runbooks. The agent should return facts, a timeline, one to three evidence-ranked hypotheses, confidence, unknowns, safe next checks, and deep links; it must say “possible cause” unless the evidence is deterministic. Its service identity must have no shell, general HTTP, database write, Redis command, RabbitMQ mutation, secret, raw PII, provider credential, or production-management permission. Enforce fixed query templates, environment/service scope, result-size and time-window caps, output redaction, audit records, and human approval for every ticket severity decision or remediation. Treat log lines, alert annotations, trace attributes, and even runbook text as untrusted prompt-injection input. OpenTelemetry’s security guidance explicitly treats telemetry as sensitive application and traffic data requiring protection against tampering ([OpenTelemetry security](https://opentelemetry.io/docs/security/)).

## Four gates turn the roadmap into a safe release

**Gate one** hardens the operational baseline: production secrets and tenant provisioning, private or authenticated management endpoints, tested redaction, retention rules, and delivery/provider failure runbooks. **Gate two** delivers truthful status: provider adapter, callback verification, immutable attempts/events, status API, dashboards, and SLO alerts. It is complete when support can answer what happened to one notification without consulting raw logs.

**Gate three** adds correlated observability: JSON events, OTLP traces, HTTP-to-RabbitMQ propagation, low-cardinality domain metrics, synthetic failure tests, and a dashboard-to-trace-to-log path. It is complete when an on-call developer can determine affected channel and scope, failure class, queue/retry state, and an example trace without AI. **Gate four** deploys the authenticated incident-enricher and then the read-only agent behind evaluation gates. Use sanitized historical incidents and fault injection to measure factual grounding, report usefulness, redaction failures, duplicate incidents, cost, and time to useful triage; promote it only if it materially reduces investigation time without broadening production access.

## Conclusion

The best next feature is not “AI observability”; it is **accountable delivery**. Status callbacks and an attempt ledger turn the service from a reliable asynchronous sender into a product customers can trust, while signed webhooks, templates, preferences, and scheduling extend that trust in a controlled order. The existing Prometheus/Grafana work means the service is already well positioned to begin observability, but it needs correlated, privacy-safe evidence before automation can be credible.

Build the agent as a narrowly scoped reader of that evidence, never as an autonomous fixer. That boundary converts it from an attractive but unsafe log-search chatbot into a practical incident-reporting capability: useful on the first bad day, measurable over time, and safe to expand only when the evidence proves it deserves more responsibility.
